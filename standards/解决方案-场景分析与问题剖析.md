# 解决方案-场景分析与问题剖析 写作规范

版本：v2.1（2026-08-03）
适用：流程二 / 产出 `解决方案/01_场景分析与问题剖析.md`
模板：`references/solution-templates/01_场景分析与问题剖析.md`
执行方式：本规范 + `通用写作规范.md` **同时生效**（反 AI 腔、过度声称护栏、术语保护、完整性底线见通用规范）。

## 1. 写作目标

- 把「真实场景」翻译成「可解决的问题」，并证明**为什么值得解决**（重要性论证）；
- 通过已有研究对比，说明当前场景的空白与机会；
- 定下**成功标准、数据可行性、资源约束与风险**，让 02 方案和 03 架构有明确约束。

## 2. 结构要求

1. 场景描述（应用场景、环境约束、目标用户）；
2. 问题定义（一句话问题、输入/输出、评价指标）；
3. **问题重要性论证（Why it matters）**：为什么现在值得解决（时机）、不解决的代价、学术/实际价值、与流程一文献中「未来工作/空白」的对应；
4. 已有研究对比（表格：思路/优点/局限/差距/来源）；
5. 问题剖析（难点、现有方案不适用的原因、机会点）；
6. **成功标准（可测量）**：本方案达到什么可量化结果算成功（指标 + 阈值，对应 02 实验指标与 03 验收）；
7. **数据可行性核查**：数据可得性、规模、质量、标注成本、隐私/许可；缺失部分明确标注「需获取」；
8. **资源约束**：算力、时间、人力（量化，如「单卡 24G、4 周内」），影响方法选型（见 02 规范 §3.2 资源适配）；
9. **风险与缓解**：技术/数据/时间风险清单 + 缓解策略 + 触发回访条件；
10. 方案边界（做什么/不做什么、假设、风险）。

## 3. 语言与表达

- 场景描述要具体（数据规模、资源限制要写数字，不写「数据量较大」这类空话）；
- 对比表每行都要有「与当前场景的差距」这一列，这是本文件的灵魂；
- 评价指标与成功标准必须可量化；
- 对比结论的措辞不得超过证据强度：现有方案写「受限于 / 未覆盖」，不写「无法解决 / 全面落后」（过度声称护栏见 `通用写作规范.md` §2）；
- 重要性论证要克制：写「解决了文献中 X 指出的空白」（附来源），不写「填补了空白」这种无据断言；
- 全文过一遍反 AI 腔自检（通用规范 §1）。

## 4. 引用与溯源

- 对比行引用流程一文献必须用 Obsidian wikilink `[[论文/<主题>/<论文短名-年>/<md文件名>|<作者 年份>]]` 可点击跳转到对应论文 MD（禁止纯文本 `[序号]` / 作者-年份，见 `standards/通用写作规范.md` §4）；
- 引用基于流程一文献综述，不新增未检索文献；
- 禁止编造已有研究、数据、指标；
- 对已有研究的负面评价必须附证据（原文献的局限描述或对比数据），不写无根据的贬低；
- 重要性论证中的「空白/未来工作」必须可溯源到文献或综述的结论。

## 5. 检查清单

- [ ] 问题定义一句话能说清
- [ ] 问题重要性论证有文献依据（对应综述中的空白/未来工作）
- [ ] 评价指标可量化
- [ ] 对比表每行都有差距列与来源
- [ ] 成功标准明确（指标 + 阈值）
- [ ] 数据可行性核查完整（可得/规模/质量/标注/许可）
- [ ] 资源约束量化（算力/时间/人力）
- [ ] 风险清单与缓解策略齐全
- [ ] 难点清单覆盖全部关键挑战
- [ ] 方案边界明确（不做什么也写清了）
- [ ] 负面评价均有文献证据支撑
- [ ] 通过通用规范反 AI 腔与过度声称自检
