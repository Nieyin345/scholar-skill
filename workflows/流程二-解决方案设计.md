# 流程二：解决方案设计（v2.0）

本文件是 `scholar` Skill 流程二的详细步骤。**前置依赖：已完成流程一**（对整个方向有全面了解，主题文件夹已存在）。
共享脚本与参考文档位于 skill 根目录：`scripts/` 与 `references/`（见 `SKILL.md` 的共享索引）。

v2.0 升级要点（参考来源见文末）：问题类型确认（研究问题分类 → 方法族）；02 每篇方案生成后做**轻量批判审查**；第二篇方案后先产出**方案对比矩阵**再让用户选 03 方案；03 完成进入流程三前设**方案评审门禁**（先评审后施工）；新增 `解决方案/README.md` 决策日志；01 补充问题重要性论证/成功标准/数据可行性/资源约束/风险与缓解。

---

## 前置条件

- 已存在流程一产出的主题文件夹：`论文/<检索主题>/`
- 已存在 `文献综述.md`（或至少 `01_检索结果.md`）作为方案依据
- 缺少前置产物时：提示用户先执行流程一，不强行开始

## 触发条件

- 用户要求：方案设计 / 解决方案 / 技术方案 / 怎么实现 / 架构设计 / 算法选型 / 代码结构
- 或用户说「完成流程一后继续做方案」

## 触发模式（可拆可合）

- **完整**：01 + 02（一篇或多篇方案）+ 对比矩阵 + 03 全部产出
- **单独**：只产出其中一份（如只要代码架构 03）
- **组合**：任意组合

## 逐篇生成规则（重要）

- **每个对话只生成一篇 MD**，不一次产出多篇；
- 每篇生成完询问用户下一步：
  1. 01 完成后 → 问「继续生成方案文档（02）吗？」
  2. 每篇 02 方案完成后 → 问「要继续生成下一篇方案吗？」
  3. **第二篇 02 方案完成后 → 先产出「方案对比矩阵」→ 再问「03 代码架构设计要用哪个方案？」**，用户选定后再生成 03；
- 03 只基于用户选定的那个方案生成。

## 流程步骤

### 1. 确认需求与问题类型

- 确认本次要产出哪一份文档（按逐篇生成规则推进，不默认一次全出）；
- 与用户确认场景细节：真实使用场景、数据情况、资源限制、目标指标；
- 确认方案深度（概念方案 / 可落地实施方案）；
- **确认问题类型（决定方法族，参考 research-methodology 分类）**：探索性 / 描述性 / 比较性 / 关联·预测 / 因果 / 机理——02 的方法选型从对应方法族出发，不反向（见 `standards/解决方案-实现逻辑与方案设计.md` §3.1 决策树）。

### 2. 创建目录

在流程一的主题文件夹下创建解决方案子文件夹：

```text
论文/<检索主题>/
├── 01_检索结果.md
├── 文献综述.md
├── <论文文件夹>/
└── 解决方案/
    ├── README.md                       ← 决策日志：方案演进、选型理由、评审结论
    ├── 01_场景分析与问题剖析.md
    ├── 02_实现逻辑与方案设计-方案A.md
    ├── 02_实现逻辑与方案设计-方案B.md
    ├── 02_方案对比矩阵.md              ← 第二篇方案生成后产出
    └── 03_代码架构设计.md
```

- `README.md` 记录：方案清单、每篇状态（草稿/已评审/已选定）、选型决策（date/decision/why）、评审结论——每次会话先读、结束后更新（参考 research-manager 状态持久化）。

### 3. 按模板逐篇产出文档

每份文档的**写作规范**见 `standards/` 对应文件，按规范执行（结构、语言、检查清单）：

- 文档一 → `standards/解决方案-场景分析与问题剖析.md`（v2.1）
- 文档二（每篇方案）→ `standards/解决方案-实现逻辑与方案设计.md`（v3.1：方法论，一个方案一篇 MD）
- 文档三 → `standards/解决方案-代码架构设计.md`（v3.2：架构层面，基于用户选定的方案）

| 文档 | 模板 | 内容要点 |
|------|------|----------|
| 01_场景分析与问题剖析.md | `references/solution-templates/01_场景分析与问题剖析.md` | 场景描述、问题定义、**问题重要性论证**、已有研究对比、问题剖析、方案边界、**成功标准**、**数据可行性**、**资源约束与风险** |
| 02_实现逻辑与方案设计-方案X.md | `references/solution-templates/02_实现逻辑与方案设计.md` | 方案概述、问题形式化、方法选型（**问题类型决策树**）、算法设计、数学与理论（伪代码）、数据方案、**4 阶段渐进实验设计**、效度与局限、决策记录 |
| 03_代码架构设计.md | `references/solution-templates/03_代码架构设计.md` | ADR、架构总览图、技术栈、目录结构、模块接口、数据流、测试与验证回路、**实现顺序对齐 4 阶段实验**、演进维护、学术场景适配 |

**写作要求（与流程一共用规则）：**

1. **完全基于流程一的文献基础**：对比已有研究时标注来源（`[序号]` 或作者-年份，对应 `01_检索结果.md`）；禁止编造不存在的文献、数据、指标。
2. 每一处关键决策记录「为什么选 / 为什么不选」，可审计（写入文档决策记录 + `README.md` 决策日志）。
3. 文档之间保持一致性：问题定义 ↔ 方案设计 ↔ 代码结构一一对应；03 与选定方案（02-方案X）的模块、接口、数据流一致。
4. 不确定的假设明确标注，需要用户确认的放在文档开头或末尾的「待确认」区。

### 4. 02 方案批判审查（每篇生成后，轻量）

每篇 02 方案生成后，在交付给用户前做一轮**轻量批判审查**（参考 critical-analysis，输出附在方案文档末尾或 `README.md`）：

- **论证映射**：核心主张（「本方案有效」依赖哪些前提）；
- **证据清单**：每个前提的证据质量（来自流程一文献？估计？待验证？）；
- **逻辑审计**：是否有非 sequitur、因果混淆、把「相关性」写成「因果」；
- **偏差审计**：是否只挑了支持自己的证据（cherry-picking）、是否高估了方法优势；
- **替代解释**：列出 2–3 个与本方案竞争的替代假设（对应消融设计）；
- **总判定**：Strong / Moderate / Weak + 下一步（进入对比矩阵 / 需要修订 / 需要更多证据）。

审查只做「判断与建议」，修订由下一轮对话完成；发现**证据不足（非写作问题）**时告知用户：可能需要回到流程一补检索，或降低方案声称强度。

### 5. 方案对比矩阵（第二篇 02 方案生成后）

第二篇方案生成后、用户选定 03 方案前，产出一页 `02_方案对比矩阵.md`：

| 维度 | 方案A | 方案B | … |
|------|-------|-------|---|
| 核心思路（一句话） | | | |
| 问题形式化（共用） | 同一 | 同一 | 同一 |
| 评价指标（共用） | 同一 | 同一 | 同一 |
| 优势（证据支撑） | | | |
| 主要风险/局限 | | | |
| 数据需求 | | | |
| 计算/资源需求 | | | |
| 实现复杂度 | | | |
| 新颖性（相对文献） | | | |
| 适配当前场景 | | | |
| 综合建议 | | | |

- 对比矩阵**不评分排序替用户做决定**，只把差异摆清楚 + 给建议；
- 用户选定方案后，把选型决策（date/decision/why）写入 `README.md` 决策日志。

### 6. 03 代码架构设计（基于选定方案）

- 03 只基于用户选定的方案生成，模块/接口/数据流与选定 02 方案一一对应；
- 实现顺序**对齐 4 阶段渐进实验**（experiment-design）：阶段1 初始实现（简单数据集跑通）→ 阶段2 基线调优（不改架构，≥2 数据集）→ 阶段3 创造性改进（≥3 数据集）→ 阶段4 消融；每阶段对应 03 的「实现顺序」章节与验收测试。

### 7. 方案评审门禁（进入流程三前，先评审后施工）

03 生成完成后、进入流程三（代码实现）前，执行**方案评审门禁**（参考 gstack「先评审后施工」+ superpowers 验证纪律）：

1. **自检**：03 对照 `standards/解决方案-代码架构设计.md` 检查清单逐条过（依赖规则/可测性/ADR/输出目录/学术适配）；
2. **批判审查**：对整套方案（01+02+03）做一轮 critical-analysis 式审查，重点：方案是否覆盖 01 定义的全部难点、02 是否区分竞争假设、03 是否每个模块可测；
3. **一致性核对**：问题定义 ↔ 方案 ↔ 代码结构 ↔ 评价指标一一对应；文献引用无编造；
4. **用户确认**：把评审结论（通过 / 需修订）提交用户，用户确认后才进入流程三。

**门禁不通过** → 修订对应文档后重审，不带着未解决的问题进入流程三（负面判据：问题未清空不得声称完成）。

## 说明

- 流程二不需要脚本，只产出 Markdown 文档；
- 本流程仅在文件发生变动时（创建/删除/重命名/移动/转换完成）更新项目导航文档 `00_项目导航.md`，无文件变动的轮次不重写（规则见 `SKILL.md`「项目导航文档（强制）」）；
- 文档与论文放在同一主题文件夹下，便于统一管理；
- 02 是方法论（算法+数学），03 是代码架构（含测试驱动与验证），二者不重叠；
- 03 通过评审门禁后，流程三（代码实现）直接复用本流程的 03_代码架构设计.md。
