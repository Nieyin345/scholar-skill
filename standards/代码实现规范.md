# 代码实现规范

版本：v1.1（2026-08-03）
适用：流程三 / 产出：按 `03_代码架构设计.md` 生成的代码文件与测试
执行方式：本规范 + `通用写作规范.md` **同时生效**（反 AI 腔、过度声称护栏、术语保护、完整性底线见通用规范）。

> 定位：本规范回答「代码怎么写才对」。与 02（方法论：算法+数学）、03（架构：怎么组织）配合：02 说用什么方法，03 说怎么拆，本规范说**每一行怎么写**。核心三指标与 03 一致：可测试、可维护、可读。v1.1 起补充「写错了怎么调」：系统化调试（§6）与验证证据（§7），与流程三工作流 v2.0 对齐。

## 1. 写作目标

- 把 03 架构文档变成**可运行、可测试、可维护、可读**的代码；
- 代码是给读者看的（读/写比 >10:1），优先为读者优化；
- 每个阶段产出「测试 + 实现 + 验证证据」三件套。

## 2. 实现原则

1. **架构一致**：目录即架构；接口签名与 03 一致；核心不依赖框架/DB（依赖规则不被破坏）；
2. **测试先行（TDD 铁律）**：无失败测试不得写生产代码；先看测试失败（且失败原因正确）→ 最小实现 → 重构；
3. **验证闭环**：完成声明必须附 fresh 验证输出；测试失败据错误信息改代码后重跑；
4. **系统化调试**：无根因调查不修复；禁止「随便改改再跑」「多改几处一起跑」；3 次修复失败即怀疑架构（§6）；
5. **最小变更**：只实现当前阶段需要的，不投机添加（YAGNI）；
6. **库优先**：先找现成库/工具，不重复造轮子；确需自写才自写（业务逻辑/性能关键路径/安全敏感）；
7. **Boy Scout 规则**：改动过的代码，离开时比来时更干净。

## 3. 编码规范

### 3.1 命名

- 命名揭示意图：变量/函数/类名能回答「为什么存在、做什么、怎么用」；
- 类名用名词，函数名用「动词 + 名词」；布尔用谓词式（`is_valid`、`has_permission`）；
- 一个概念一个词：不混用 `fetch / retrieve / get`；
- 避免无意义缩写与匈牙利命名；短变量名只用于极小作用域循环计数；
- 常量用 `UPPER_SNAKE_CASE`，文件/函数/变量按语言惯例（Python `lower_snake_case`）。

### 3.2 函数

- 函数小且单一职责：理想 4-6 行，最多不超过 80 行；超过就拆分；
- 参数尽量少（0-2 个）；一个抽象层级，不混合高层与低层；
- 早返回优于深嵌套（嵌套超过 3 层必须重构）；
- 文件超过 200 行拆分为多个文件。

### 3.3 注释

- 注释解释 **WHY**，不解释 WHAT（WHAT 由好命名表达）；
- 不写废话注释（`count++  # 计数器加1`）；
- 公共接口写简短 docstring（用途、参数、返回、抛错）；
- 遗留问题用标记：`TODO`（后续工作）、`FIXME`（已知错误行为）、`NOTE`（非显而易见的决策）。

### 3.4 错误处理

- 显式处理错误，不静默失败（要么抛错，要么记录日志）；
- 外部调用（网络/IO）必须有错误处理与重试/超时；
- 错误消息可定位（包含上下文：哪个操作、什么状态码/原因）；
- 释放资源：异常路径也要清理（`with` / `try-finally`）。

### 3.5 不可变性与数据

- 默认不可变：不原地修改传入的数据结构（复制后再改）；
- 魔法数字改为命名常量（`MAX_RETRIES` 而非 `3`）；
- 不用 `any`/动态类型偷懒（有类型系统就写类型）。

### 3.6 代码味道（自检）

| 味道 | 症状 | 修复 |
|------|------|------|
| 长函数 | 函数 >80 行 | 按职责拆分 |
| 深嵌套 | if 嵌套 >3 层 | 早返回 / 提取函数 |
| 魔法数字 | 裸数字无命名 | 提取命名常量 |
| 重复代码 | 复制粘贴 | DRY 提取公共逻辑 |
| 注释废话 | 注释复述代码 | 删注释、改命名 |
| 上帝对象 | 一个类做所有事 | 按 SRP 拆分 |

## 4. 测试规范

- 测试结构用 **AAA**（Arrange 准备 / Act 执行 / Assert 断言）；
- 测试命名描述行为：`test_returns_empty_list_when_no_match`，不用 `test_works`；
- 一个测试只验证一个行为（名字里出现 and 就拆分）；
- 优先测真实代码，mock 只在不可避免时（外部服务/IO）使用；
- 测试确定性：随机性必须固定种子；
- 覆盖率要求：核心逻辑关键路径全覆盖；不做覆盖率崇拜，重点在行为验证；
- 测试先红后绿：每个新功能先写失败测试并**确认失败原因正确**（功能缺失，而非语法/断言错误）；
- 修完 bug 必须补回归测试，并做「红-绿-红-绿」验证：通过 → 撤销修复**必须失败** → 恢复 → 通过（只写测试没验证「红」= 测试无效）。

## 5. 语言与表达（代码即文档）

- 命名与领域语言一致（与 02/03 文档同一术语，见通用规范 §3.1 术语冻结）；
- 提交说明 / 交付说明简洁可读：做了什么、验证了什么；
- 不写「看起来没问题」这类无证据描述，交付时给命令与输出。

## 6. 系统化调试（v1.1 新增）

**铁律：没有根因调查，不许提修复方案。** 对任何测试失败 / bug / 意外行为，先完成四阶段，再谈修复。

1. **根因调查**：读错误消息与堆栈（行号/文件/错误码）→ 稳定重现（记录步骤与频率）→ 检查最近改动（git diff / 新依赖 / 环境差异）→ 多组件系统在每层边界加诊断输出定位断裂层；
2. **模式分析**：找相似的正确实现对比 → 列出「正确 vs 错误」每个差异（不假设「那个不影响」）→ 理解依赖与假设；
3. **假设与最小验证**：写下具体假设「我认为 X 是根因，因为 Y」→ 只做最小改动验证该假设（一次一个变量）→ 无效则换新假设，不叠加修复；
4. **实施修复**：先写能复现该 bug 的失败测试 → 单一修复（不做「顺手」改进）→ 验证通过且无回归。

规则：

- **3 次修复失败**：停止修症状，怀疑架构问题（每次修复都暴露新耦合/状态问题 = 模式可能不对），记录并询问用户，不擅自重构；
- **防御纵深**：根因修复后，在相关边界加多层校验（重试/超时/日志/状态校验），防止同类问题复发；
- **条件等待**：环境/时序问题用「轮询条件成立」替代固定 sleep，带超时与错误信息；
- **真环境问题**（完成全部调查后）：记录调查过程与证据，加监控/日志后标记「已调查，待观测」，不轻易下「无根因」结论（95% 的「无根因」是不充分调查）。

## 7. 验证证据规则（v1.1 新增）

**铁律：没有 fresh 验证证据，不许声称完成。** 完成任何声明前执行五步门禁：

1. **IDENTIFY**：什么命令能证明这个声明？
2. **RUN**：执行完整命令（fresh 运行，不看历史输出）；
3. **READ**：读完整输出、看退出码、数失败数；
4. **VERIFY**：输出是否真的支持声明？否 → 如实报告实际状态；
5. **ONLY THEN**：才作声明。

- 证据必须**附输出**（命令 + 结果），不写「应该没问题 / 看起来正常 / 我确信」这类无证据描述；
- **红旗词**：should / probably / seems / 应该没问题 / 看起来正常——出现即回去验证；
- **回归验证**：修完 bug 用「红-绿-红-绿」验证回归测试有效（通过 → 撤销修复必须失败 → 恢复 → 通过）；
- 委托/子代理的结果也要独立验证（查 VCS diff + 跑测试），不信任自报「成功」。
