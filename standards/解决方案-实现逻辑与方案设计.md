模板：`references/solution-templates/02_实现逻辑与方案设计.md`
执行方式：本规范 + `通用写作规范.md` **同时生效**（反 AI 腔、过度声称护栏、术语保护、完整性底线见通用规范）。

> 本规范定位：**方法论**。回答「用什么方法解决、为什么、数学上成不成立」。只涉及**算法与数学**，**不涉及代码**（代码组织归 03 代码架构设计）。同一问题允许有多个方案，一个方案一篇文档。

## 1. 写作目标

- 把 01 定义的问题翻译成「方法方案」：怎么建模、用什么算法、为什么、数学上是否成立、怎么验证；
- **一份方案一篇 MD**：同一问题可以有多个方案（如 方案A：基于 X 算法；方案B：基于 Y 算法），每篇独立完整，可对比；
- 每篇方案都能自证三件事：核心思路是什么、什么情况下它优于替代方案、什么情况下不如。
- **先读后写（铁律）**：动笔前通读核心文献（`03_文献综述.md` + 关键论文 MD 全文）与 01；算法选型、与已有方法对比、数学假设必须来自已读文献，禁止凭模型既有知识虚构方法效果 / 对比数据；

## 2. 多方案与逐篇生成工作流

- 02 阶段允许产出**多篇方案文档**，命名：`02_实现逻辑与方案设计-方案A.md`、`02_实现逻辑与方案设计-方案B.md`……统一放 `解决方案/` 子文件夹；
- **每个对话（一次交互）只生成一篇 MD**，逐篇推进：
  1. 第一篇：基于 01（场景分析）生成默认推荐方案（或用户指定方向的方案）；
  2. 生成完第一篇 → 询问用户「**要继续生成下一篇方案吗？**」；
  3. 用户确认 → 生成第二篇（与第一篇不同方法的方案）；
  4. **第二篇完成后 → 先产出 `02_方案对比矩阵.md`（见流程二工作流步骤 4）→ 再询问用户「第三篇（03 代码架构设计）要用哪个方案？」**，用户选定后，03 基于该方案生成；
- 方案之间必须**可对比**：共用同一问题形式化与同一评价指标，仅方法不同；
- 方案篇数由用户决定（至少 2 篇起，可更多），**不擅自一次生成多篇**；
- 每篇方案独立成文，不互相引用正文（引用文献统一用 Obsidian wikilink `[[论文/<主题>/<论文短名-年>/<md文件名>|[编号]]]` 可点击跳转，见 `standards/通用写作规范.md` §4）。
- **文末参考文献**：本文档有引用时，正文结束后加 `## 参考文献` 按编号升序列出（`[[论文/<主题>/<论文短名-年>/<md文件名>|[编号] <完整参考文献>]]`），编号与正文一一对应（见 `standards/通用写作规范.md` §4）；

## 3. 方法论原则

### 3.1 问题类型决定方法（决策树）

写方案前先明确问题类型（参考 research-methodology 分类 + ARS 方法决策树），再选方法，不反向：

| 问题类型 | 关键词 | 方法族 | 算法示例（AI 场景） |
|----------|--------|--------|----------------------|
| 探索性 | What happens / 现象如何 | 探索分析、数据分析 | 聚类、可视化分析、表征学习 |
| 描述性 | Prevalence / Patterns | 观察、测量 | 统计建模、分布估计 |
| 比较性 | Differences / Improvement | 实验、基准对比 | 对比基线、SOTA 评估 |
| 关联·预测 | Association / Prediction | 相关、回归、学习 | 分类/回归、序列模型、图模型 |
| 因果 | Effect / Impact | 实验、因果推断 | 因果推断、干预、反事实 |
| 机理 | How / Why | 理论分析、机理建模 | 理论推导、可解释性、机制分析 |

- 文档必须写明：本方案对应哪类问题、为什么这类问题的常用方法族适合当前场景；
- 01 的「成功标准」与评价指标要与问题类型匹配（比较性用相对提升，预测性用绝对指标+基线差距）。

### 3.2 资源约束适配（选型前先过）

方法选型必须结合 01 的资源约束（算力/时间/数据/人力）：

- **算力有限**：轻量方法、预训练模型、小规模验证、模型压缩；不选需要大规模训练的方向；
- **时间紧**：成熟方法优先、现有工具/库、快速原型；避免从零实现；
- **数据少**：迁移学习、数据增强、few-shot、合成数据；说明数据不足时的降级方案；
- **单人项目**：避免大规模并行工程；标注「需要团队」的候选直接降权。

### 3.3 方法匹配与证据支撑

- **候选对比 ≥2**：每篇文档内给出本方案 vs 主要替代方案的对比，说清适用条件差异；
- **证据支撑**：方法选型引用流程一文献；性能数字必须有出处（文献值/估计值，标注清楚）；
- **诚实校准**：写明适用条件与不适用条件、假设前提；不确定处显式标注；
- **竞争假设**：实验设计要能区分「为什么我的方法有效」的竞争解释，而不是只堆结果。

### 3.4 创造性重构（方法卡壳时，非默认）

当常规方法族无法匹配问题、或现有方法都失败时（不是默认步骤），参考 research-methodology 的创造性重构：

- **假设反转**：说出隐藏假设（「the Box」），逐条反转——「不追求让 X 更强，而是让 X 的失败变得有用」；
- **第一性原理分解**：把问题还原到最基本的数学/物理约束，从底层重建方案；
- **跨域类比**：在远距离领域找结构相似的问题，借用其机制而非表面；**类比必须建立在已验证的科学上，禁止编造原理支撑创意跳跃**；
- 重构后的方案仍必须过效度审计（§4 第 8 项）与批判审查（工作流步骤 4）；推测性跳跃标注为「推测」。

## 4. 结构要求（每篇方案文档）

1. **方案概述**：一句话核心思路 + 对应 01 的哪个问题 + 评价指标；
2. **问题形式化**：输入/输出定义、目标函数、约束条件、假设前提、评价指标（数学表达）；
3. **方法选型**：候选算法对比表（候选算法 / 适用条件 / 时间复杂度 / 已知局限 / 选或不选理由 + 文献引用）；写明问题类型与资源约束如何影响选型；
4. **算法设计**：若自研或改进，写明改进点、动机、与基线方法的差异、理论依据；
5. **数学与理论**：建模细节、损失/优化目标、收敛性/复杂度/可解释性等理论性质（含伪代码）；
6. **数据方案**：数据来源、预处理、训练/验证/测试划分、数据量估算、类不平衡/分布偏移；与 01 数据可行性核查一致；
7. **实验设计（4 阶段渐进框架）**：参考 experiment-design，按渐进阶段组织，每阶段写明回答哪个问题：
   - 阶段1 初始实现：简单数据集跑通（功能正确性）→ 阶段2 基线调优：固定架构调超参，**≥2 数据集** → 阶段3 创造性改进：新改进/洞察，**≥3 数据集** → 阶段4 消融：组件逐项分析；
   - 基线选择（诚实调参）、评价指标与统计显著性、**每个实验对应要回答的问题**、多随机种子（默认 ≥3）；
   - 把消融设计对应到批判审查的「替代解释」清单（每个竞争假设对应一个消融）；
8. **效度与局限**：威胁有效性的因素（threats-to-validity audit）、失败模式、本方案不能回答什么；
9. **决策记录**：关键决策（备选 + 取舍 + 回访触发条件）。

## 5. 伪代码规范（数学与算法表达）

- 用**标准算法记号**（Algorithmic Notation），不是任何编程语言的代码语法；
- 定义输入/输出（`Require`/`Ensure`）、主循环/递归结构、参数与类型；
- 附带**复杂度分析**（时间/空间）或性质命题；
- 伪代码与 03 的模块/接口保持一致性：每个伪代码步骤可映射到 03 的某个模块；
- 行号便于引用；抽象层次适中（不过细到代码、不过虚到无法实现）。

## 6. 语言与表达

- 数学符号用 Markdown/LaTeX 数学表达，全文符号一致；
- 不写具体代码、库、框架（那些归 03）；
- 术语冻结：数学/算法术语不换同义词（见 `通用写作规范.md` §3.1）；
- 推测性内容（估计值、创造性重构）显式标注「推测/估计」，不用确定性语气；
- 全文过一遍反 AI 腔自检（通用规范 §1）。

## 7. 引用与溯源

- 算法/方法/定理引用流程一文献用 Obsidian wikilink `[[论文/<主题>/<论文短名-年>/<md文件名>|[编号]]]`（可点击跳转到论文 MD，禁止纯文本编号）；
- 性能数字必须来自文献或标注为估计；禁止编造；
- 与文献方法的差异要明确说明；
- 数据指标来自 01 文档的评价指标与成功标准，不新增不一致口径。

## 8. 检查清单

- [ ] 定位正确：只讲方法与数学，**无代码**
- [ ] 方案概述一句话核心思路
- [ ] 问题类型已写明（对应 §3.1 决策树）且资源约束已核对（§3.2）
- [ ] 问题形式化完整（输入/输出/目标/约束/指标）
- [ ] 候选算法对比表有选/不选理由 + 文献引用（wikilink 可点击跳转）
- [ ] 伪代码符合算法记号规范，含复杂度分析
- [ ] 伪代码步骤可映射到 03 的模块
- [ ] 数据方案完整（来源/预处理/划分/数据量，与 01 一致）
- [ ] 实验设计按 4 阶段渐进组织，每个实验对应要回答的问题，能区分竞争假设
- [ ] 消融设计覆盖批判审查列出的替代解释
- [ ] 效度与局限透明（threats-to-validity 审计，不夸大、写明失败模式）
- [ ] 决策记录含备选与取舍
- [ ] 已做轻量批判审查（论证映射/证据清单/逻辑审计/偏差审计/替代解释，见工作流步骤 4）
