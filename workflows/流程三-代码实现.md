# 流程三：代码实现（v2.1）

本文件是 `scholar` Skill 流程三的详细步骤。**前置依赖：已完成流程二**，存在选定方案对应的 `解决方案/03_代码架构设计.md`。
共享脚本与参考文档位于 skill 根目录：`scripts/` 与 `references/`（见 `SKILL.md` 的共享索引）；本流程**不需要脚本**，是纯 MD 指令流程——由 Agent 直接按规范写代码并运行测试验证。

## 前置条件

- 已完成流程二，存在：
  - `解决方案/01_场景分析与问题剖析.md`（问题定义与评价指标）
  - `解决方案/02_实现逻辑与方案设计-方案X.md`（用户选定的方案：算法与数学）
  - `解决方案/03_代码架构设计.md`（基于选定方案的架构：目录、模块、接口、测试策略、学术场景适配）
- 03 中已定义**实现顺序**（v3.2 起对齐 4 阶段渐进实验：阶段1 初始实现 → 阶段2 基线调优 → 阶段3 创造性改进 → 阶段4 消融）；本流程按该顺序执行，不跳步。
- **先读后写（铁律）**：实现前按需回读 `02_实现逻辑` 与关键论文 MD 的方法细节（算法公式 / 超参 / 实验设置），不凭记忆猜实现细节；实现与论文方法不一致时记录并询问用户。
- 缺少前置产物时：提示用户先执行流程二，不强行开始。

## 触发条件

- 用户要求：写代码 / 实现 / 开始开发 / 落地 / 把方案做成 / implement / code it
- 或用户说「流程二完成后继续实现」

## 触发模式（可拆可合）

- **完整**：按 03 的实现顺序全部实现（阶段1 → 阶段2 → 阶段3 → 阶段4）
- **按阶段**：只实现 03 的某一实验阶段（如只做阶段1 初始实现 / 阶段3 创造性改进）
- **按模块**：只实现某个模块（对照 03 的模块表）
- 每个对话默认只推进一个阶段/模块，完成并验证后再询问是否继续下一步。

## 流程步骤

### 1. 确认实现范围

- 读取 `03_代码架构设计.md`，向用户确认本次实现范围（完整 / 阶段 / 模块）；
- **实现顺序对齐 03 的 4 阶段实验**：确认本次对应哪个实验阶段，前一阶段产物是否已存在并通过验收（阶段不跳步，除非用户明确要求）；
- 确认技术栈与本机环境（Python 版本、依赖、GPU 等）；
- 确认运行/测试/验收命令（`pytest`、`npm test` 等，以 03 文档的验收命令为准）——这些命令就是后面「验证门禁表」的证据来源。

### 1.5 实现前最小化决策（梯子模型，借鉴 ponytail）

**写任何生产代码前，先爬梯子，停在第一个成立的梯级**（刻意克制，不是省略步骤）：

1. **这东西需要存在吗？**（YAGNI）投机需求 /「以后可能用到」→ 跳过，一句话说明为什么不做；
2. **代码库已有？** 同模块或邻近文件已有 helper / util / 类型 / 模式 → 复用。先找再写，重复实现隔壁已有的东西是最常见的浪费；
3. **标准库能做？** 用它（`re`、`pathlib`、`functools.lru_cache` 等）；
4. **原生平台功能能覆盖？** 用它（DB 约束而非应用层校验、平台内建能力而非手写）；
5. **已装依赖能解？** 用它。**绝不为一两行功能新增依赖**；
6. **一行能解决？** 就一行；
7. **只有到这一步才写最小可行实现。**

**懒于方案，绝不懒于阅读**：梯子运行在**理解问题之后**，而不是替代理解。先读任务涉及的全部代码、trace 真实流程端到端，再爬梯子；跳过理解的「懒」是危险的懒（小 diff + 自信的错误修复）。

**与 03 架构的关系**：03 定义的模块、接口、依赖方向**必须全部实现**（架构不砍），砍的是模块**内部**的膨胀（投机抽象、冗余封装、多余配置）。发现 03 本身有冗余设计 → 记录并询问用户，不擅自删架构。

**安全底线（lazy, not negligent）**：信任边界输入校验、防数据丢失的错误处理、安全措施、无障碍基础、用户明确要求——这些**绝不**为了省代码砍掉。

**Bug 修复 = 根因，不是症状**：修 bug 前 grep 该函数的**所有调用者**；在共享函数修一次（一个守卫）优于在每个调用点打补丁——只补丁报告指出的路径会让兄弟调用点仍然损坏。最小 diff 本身就是根因修复。

**延迟捷径要标注**：有意简化且有已知上限的（全局锁、O(n²) 扫描、朴素启发式）用 `# ponytail: <上限>, <升级路径>` 注释标注，记入台账，防止「以后再说」变成「永远不做」。

### 2. 创建目录

严格照 `03_代码架构设计.md` 的目录结构创建项目目录（目录即架构，不允许自由发挥）：
核心 / 适配器 / 配置组合根 / 测试 分层，核心不依赖框架与 DB。
产出位置：`论文/<主题>/implementation/`（与 `解决方案/` 并列，便于归档）。

### 3. 按阶段 TDD 实现

每个阶段固定循环（**测试先行，铁律**）：

1. **RED**：先写一个失败测试（描述该阶段要的行为，命名清晰、单一断言目标）；
2. 运行测试，确认它**因功能缺失而失败**（不是语法错误、不是断言写错），记录失败输出；
3. **GREEN**：写最小实现代码，让该测试通过；
4. 运行全部测试，确认全绿且输出干净；
5. **REFACTOR**：清理重复、改善命名、提取辅助，保持测试全绿；
6. 结束本阶段，向用户汇报验证证据（命令 + 输出），询问是否进入下一阶段/模块。

**最小实现的选择**：GREEN 阶段的最小实现用 §1.5 梯子模型选出——先查复用 / 标准库 / 已装依赖，再写；**测试也 YAGNI**：平凡的一行逻辑无需测试，非平凡逻辑（分支 / 循环 / 解析 / 金额与安全路径）至少留一个 runnable check（`assert` 自检或一个 `test_*.py`），不为投机功能写测试。

**REFACTOR 后加一轮简化审查（借鉴 ponytail-review）**：对本次 diff 做过度工程审查，一行一条发现：`L<line>: <tag> <什么>。 <替代>`。tag 与格式见 `standards/代码实现规范.md` §8；审查只列删减清单不立即动手，结论以 `net: -<N> lines possible` 结束。正确性 bug / 安全漏洞 / 性能问题**不在**本轮范围（走 §4/§5 正常流程）。

**TDD 卡住时（失败与恢复路径）**：

| 卡住情形 | 判定 | 处理 |
|----------|------|------|
| 写不出失败测试 | 对行为/边界不明确 | 回到 03/02 澄清接口与行为，或向用户确认；不凭猜测硬写 |
| 测试报错而非失败 | 语法错误、import 错误、fixture 错误 | 先修测试本身（这是测试代码的 bug），再回到 RED 确认「因功能缺失而失败」 |
| 测试「无用失败」 | 断言写错 / 测试即使功能正确也总失败 | 修正断言，确保测试能真实区分「有功能」与「无功能」 |
| 同一失败多次修复无效 | 已尝试 ≥3 次修复仍失败 | 停止修症状，按 §4 系统化调试回到根因调查；怀疑架构问题则记录并询问用户 |

### 4. 系统化调试协议（测试失败 / 实现不通过时强制）

**铁律：没有根因调查，不许提修复方案。** 禁止「随便改改再跑」「多改几处一起跑」；95% 的「无根因」是不充分调查。

四阶段（必须按顺序完成）：

1. **根因调查**：仔细读错误消息与堆栈（行号/文件/错误码）→ 稳定重现（记录确切步骤，能否每次都触发）→ 检查最近改动（git diff / 新依赖 / 环境差异）→ 多组件系统在每层边界加诊断输出，定位断裂层；
2. **模式分析**：找代码库里相似的正确实现做对比 → 列出「正确 vs 错误」的每个差异（不假设「那个不影响」）→ 理解依赖与假设；
3. **假设与最小验证**：写下具体假设「我认为 X 是根因，因为 Y」→ 做**最小**改动只验证该假设（一次只动一个变量）→ 有效才继续，无效则形成新假设，不叠加修复；
4. **实施修复**：先写能复现该 bug 的失败测试 → 实施**单一**修复（不做「顺手」改进）→ 验证测试通过且其他测试未被破坏。

**环境/时序类问题**：若完成全部调查后结论是「真环境问题 / 时序问题 / 外部服务问题」：
- 记录调查过程（查了什么、证据是什么）；
- 用**条件等待**替代固定 sleep（轮询直到条件满足，带超时与错误信息）；
- 加**防御纵深**（多层校验、重试、超时、日志）；
- 不轻易下「无根因」结论——标记为「已调查，待观测」，加监控/日志后再验证。

**3 次修复失败后**：停止继续修症状，怀疑架构问题（每次修复都暴露新的耦合/状态问题 → 模式本身可能不对），记录问题并询问用户是否调整架构，不擅自重构。

### 5. 验证门禁表（无证据不得声称完成）

完成任何声明（阶段完成 / bug 修复 / 全部完成）前，按 verification-before-completion 门禁执行：

1. **IDENTIFY**：什么命令能证明这个声明？（测试通过 → 测试命令；lint 干净 → lint 命令；构建成功 → 构建命令；修复完成 → 复现测试通过）
2. **RUN**：执行**完整**命令（fresh 运行，不看历史输出）；
3. **READ**：读完整输出，看退出码、数失败数；
4. **VERIFY**：输出是否真的支持声明？否 → 如实报告实际状态与证据；
5. **ONLY THEN**：才作出声明。

| 声明 | 需要的证据 | 不够的证据 |
|------|-----------|-----------|
| 测试通过 | 测试命令输出：0 failures | 上次跑过 / "应该没问题" |
| lint 干净 | lint 命令输出：0 errors | 只查了部分文件 / 推断 |
| 构建成功 | 构建命令退出码 0 | lint 通过 / 日志看起来正常 |
| bug 已修复 | 复现该 bug 的测试：通过 | 改了代码 / 假定已修复 |
| 阶段完成 | VCS diff 显示改动 + 测试输出全绿 | Agent 自报「成功」 |

**红旗词**（出现即 STOP，回去验证）：should / probably / seems / 应该没问题 / 看起来正常 / 我确信——这些都不是证据。

### 6. 回归测试验证（修完 bug 后强制）

修完任何 bug 后，用「红-绿-红-绿」四步验证回归测试真的有效：

1. **写**：为这个 bug 写一个回归测试（最小复现）；
2. **绿**：跑测试 → 通过（确认修复有效）；
3. **红**：**撤销修复代码** → 跑测试 → **必须失败**（证明测试真的能抓住这个 bug；不失败 = 测试无效，继续修测试）；
4. **恢复**：恢复修复代码 → 跑测试 → 通过。
- 只写了回归测试而没做「红」验证 = 测试无效，不算完成。

### 7. 一致性自查（对照 03）

- 目录结构与 03 一致（不新增未规划的目录/文件）；
- 每个模块的关键接口签名与 03 的接口表一致；
- 依赖方向不破坏：核心不 import 框架/DB/适配器；
- 伪代码步骤（02）都能在代码中找到对应实现；
- 测试策略与 03 的「测试金字塔 + 验收命令」一致；
- 学术场景适配照 03 §4 执行（图表/结果三件套/随机种子/可复现/输出目录），不临时发挥。

### 8. 交付前自查

- 编码规范自查（命名/函数大小/注释/错误处理/代码味道）见 `standards/代码实现规范.md`；
- 本次 diff 已做简化审查（§1.5 梯子模型 + 简化审查，格式见 `standards/代码实现规范.md` §8）；
- 所有测试通过并附证据（验证门禁表 §5）；
- 修过的 bug 都有回归测试并通过红-绿验证（§6）；
- README 或运行说明（如何安装依赖、如何跑测试/运行）已给出；
- 交付后询问用户反馈，反馈更新 `standards/代码实现规范.md`（成长机制见 `standards/_INDEX.md`）。

## 阶段门禁（每阶段产出物，缺则不算完成）

| 门禁 | 产出物 / 证据 |
|------|---------------|
| 范围确认 | 用户确认的实现范围 + 对应 03 实验阶段 |
| 最小化决策 | 梯子模型走查（无投机抽象 / 无重复造轮子 / 无新增不必要依赖，§1.5） |
| RED | 失败测试 + 失败输出（因功能缺失而失败） |
| GREEN | 实现代码 + 全部测试通过输出 |
| REFACTOR | 重构后全绿输出 + 输出干净 |
| 验证 | fresh 验证输出（命令 + 结果） |
| 回归 | bug 的回归测试通过红-绿-红-绿 |
| 简化审查 | diff 简化审查（tag 行 + `net` 行数，§1.5 / 规范 §8） |
| 交付 | 运行/测试说明 + VCS diff 可见改动 |
| 导航同步 | `论文/<主题>/00_项目导航.md` 已更新（新增 `implementation/` 与模块状态） |

## 说明

- 本流程**不需要脚本**：不下载工具、不复制脚本，全部由 Agent 直接写代码 + 跑测试；
- 本流程仅在文件发生变动时（创建/删除/重命名/移动/转换完成）更新项目导航文档 `00_项目导航.md`，无文件变动的轮次不重写（规则见 `SKILL.md`「项目导航文档（强制）」）；
- **本流程只写代码**：不做架构决策（边界/接口/技术栈在 03 已定），不做学术场景设置决策（可视化、结果输出、可复现约定在 03 §4 已定义，照做即可）；
- 发现 03 架构或学术适配约定不合理时：先记录问题并询问用户，不擅自改架构文档；
- 实现过程中遇到问题先按 §4 调试协议处理，禁止跳步「顺手修」；
- 后续流程如需要（实验跑数、结果分析、论文写作），直接基于本流程的实现继续。
