版本：v3.2（2026-08-03）
适用：流程二 / 产出 `解决方案/03_代码架构设计.md`
模板：`references/solution-templates/03_代码架构设计.md`
执行方式：本规范 + `通用写作规范.md` **同时生效**（反 AI 腔、过度声称护栏、术语保护、完整性底线见通用规范）。

> 本规范定位：**架构层面**。回答「系统怎么拆、边界在哪、依赖往哪个方向指、核心逻辑能不能脱离框架/DB 单独测试」，不陷入具体代码写法（那是流程三的事）。架构的三个硬指标：**可测试性**（测试能驱动改代码）、**可维护性**、**可读性**。**学术场景适配（可视化、结果可直接插入文献、可复现）必须在本文档定义，流程三只照做，不临时发挥。**

## 1. 写作目标

- 让任何开发者拿到文档就能按图施工：知道目录怎么建、边界怎么画、接口怎么定、先写什么后写什么、**怎么验证自己写对了**；
- 让架构**可测试**：核心业务逻辑能在不启动 DB/Web/框架的情况下被测试，测试失败能定位到具体模块并驱动修改；
- 让架构**可维护**：每个昂贵决策都有记录（备选与取舍），模块边界画在变化点上，改动局部化；
- 让架构**可读**：目录结构即架构，看目录就能读出分层与依赖方向；
- 让架构**适配学术场景**：可视化与结果输出设计好出版级格式，实验结果可直接插入论文/附录，运行可复现——这些决定在架构阶段定死，流程三只执行。

## 2. 架构设计原则（写文档前先过一遍，文档要逐条体现）

### 2.1 依赖规则（Clean Architecture）

- **源码依赖指向内层**：领域/用例核心不 import 框架、DB、Web、ORM；
- 框架是细节不是架构：框架调用你的核心（依赖倒置），不是核心长在框架里；
- 边界接口由内层定义、外层实现（`UserRepository` 接口在用例层，`PostgresUserRepository` 在适配器）；
- 数据跨边界用 DTO / 纯数据对象，不用 ORM 实体或框架对象；
- 组合根（main / 装配）负责把具体实现注入边界，内层不 new 具体类。
- **文档必须能回答**：换数据库能不能不动核心逻辑？核心逻辑能不能不启动服务器就跑测试？

### 2.2 可测试性（测试驱动架构）

- 架构为测试让路：核心逻辑写成纯函数/纯对象，依赖通过接口注入，测试时 mock 边界；
- 测试金字塔：单元测试（核心逻辑，占大头）→ 集成测试（模块间）→ E2E（最少）；
- 每个模块在文档中写明「可测性说明」：怎么测、mock 什么、需要什么环境；
- **验证回路必须写进架构文档**：
  1. 每个实现阶段定义验收标准（跑什么命令、看什么输出算完成）；
  2. 测试先行（Red-Green-Refactor）：先写失败测试 → 最小实现 → 重构；
  3. 自校正规则：测试失败时**根据失败信息改代码**，改完重跑，直到全绿；禁止「看起来应该没问题」；
  4. 完成声明必须附验证证据（fresh 运行的测试输出），无证据不得声称完成；
  5. 铁律：没有「先看它失败」的测试就写的生产代码，不保留。

### 2.3 可维护性

- 模块边界画在**变化点**：高频变化处设边界，避免过早抽象（YAGNI：投机抽象是欠给想象中的未来的债）；
- 组件依赖图无环；每个模块单一职责；
- 每个昂贵决策记录 ADR：选择 + 备选 + 取舍 + **回访触发条件**（什么时候重新审视这个决策）；
- 服务是部署边界，不是架构边界——微服务配共享大表就是「分布式单体」，比干净的单体更糟。

### 2.4 可读性

- 目录结构即架构：从目录能读出分层与依赖方向；
- 命名使用统一语言（领域术语全程一致，见通用规范 §3.1 术语冻结）；
- 简单性优先：能少写就少写，删掉投机抽象，半成品产品好过半吊子。

### 2.5 反模式警戒（文档自检）

| 反模式 | 症状 | 架构对策 |
|--------|------|----------|
| 大泥球 | 无结构、互相依赖 | 引入模块边界 + 依赖规则 |
| 金锤 | 所有项目同一套架构 | 用选型决策树按需选择 |
| 意外复杂度 | 架构比领域需要更复杂 | 从简单开始，有证据再升级 |
| 简历驱动开发 | 为学新技术而选型 | 选型对齐团队能力与项目需要 |
| 供应商锁定 | 核心逻辑耦合云厂商/框架 | 边界抽象，厂商代码限适配器 |
| 分布式单体 | 微服务共享数据库 | 按业务能力划分数据边界 |

### 2.6 学术场景适配（原则）

- **结果即文献素材**：实验产出的图表、表格、指标要能直接用于论文/附录，不在实现阶段临时补；
- **可视化出版级**：图表默认矢量格式（SVG/PDF），位图 ≥300 DPI；字号、字体、配色、线宽全篇统一；图注规范（编号 + 标题 + 说明）；
- **可复现**：随机种子固定、实验配置记录（超参数/数据版本/环境）、依赖锁定；
- **实验可管理**：超参数与实验结果落盘（CSV/JSON/LaTeX 表格），支持多次重复与统计显著性。

## 3. 结构要求

1. **架构决策记录（ADR 摘要表）**：决策点 / 选择 / 备选 / 取舍理由 / 回访触发（架构风格、边界划分、技术栈、数据存储、关键模式）；
2. **架构总览图**（mermaid 或 ASCII）：分层与依赖方向，箭头必须指向核心，核心不依赖外层；
3. 技术栈（语言/框架/依赖/版本环境 + 简短选型理由，对应 ADR）；
4. 目录结构（完整目录树 + 每目录职责注释；**目录要体现分层**：核心 / 适配器 / 配置组合根 / 测试；**含结果输出目录**：`results/`、`figures/`、`tables/`）；
5. 模块职责与接口（表格：模块/职责/关键接口/依赖/**可测性说明**）；
6. 数据流（输入 → 适配器 → 用例 → 实体 → 输出，标注每环节数据形态；跨边界用 DTO）；
7. **测试策略与验证回路**（金字塔、每模块测试点、阶段验收命令、自校正规则、评价指标映射）；
8. 实现顺序（分阶段，每阶段必须带「验收测试」；**对齐 4 阶段渐进实验**：阶段1 初始实现（简单数据集跑通）→ 阶段2 基线调优（不改架构，≥2 数据集）→ 阶段3 创造性改进（≥3 数据集）→ 阶段4 消融；每阶段对应 02 实验设计中的阶段与验收指标）；
9. 演进与维护（换 DB 改哪里、加模块怎么加、拆服务触发条件，对应 ADR 回访）；
10. **学术场景适配**（可视化、结果输出、可复现与实验管理——见 §4）。

## 4. 学术场景适配要求（在架构文档中必须写清，流程三照做）

### 4.1 可视化设计

- 流程图 / 架构总览 / 训练与推理管线等用 **Mermaid 内嵌 md**（Obsidian 原生渲染，随笔记跳转，见 `tools/科研插图.md`）；出版级矢量图（神经网络结构图等）按 `tools/科研插图.md` 导出 SVG/PDF 到 `figures/`；
- 列出本实验需要产出的图表清单（损失曲线、指标对比图、混淆矩阵、消融图、注意力可视化等，对应 02 的实验设计）；
- 每种图表定格式：矢量优先（SVG/PDF），位图 ≥300 DPI；画布尺寸与论文单栏/双栏匹配；
- 定统一风格：字体、字号、配色、线宽、图例位置、坐标轴命名；
- 图注规范：`Figure N: 标题。说明（含统计信息）`，表格 `Table N: ...`；
- 图表生成代码放在独立模块（如 `reporting/` 或 `viz/`），不散落在实验脚本里。

### 4.2 结果输出（可直接插入文献）

- 指标结果导出格式：CSV（原始数据）+ JSON（元数据）+ LaTeX 表格（论文用），三件套；
- 输出目录约定：`results/`（指标与日志）、`figures/`（图表）、`tables/`（表格）；命名带实验标识；
- 每个实验记录：配置、指标、随机种子、运行时间、环境版本。

### 4.3 可复现

- 固定随机种子（全局 + 各库）；随机性来源全部可指定；
- 实验配置（超参数、数据版本、预处理参数）记录进 `config/` 且随结果保存一份；
- 依赖锁定（`requirements.txt` / lockfile），注明 Python/框架/GPU 版本。

### 4.4 实验管理

- 支持多次重复实验（`--repeat N` 或等价机制），输出均值/方差/置信区间；
- 统计显著性检验的位置与方法在架构文档中列出（对应 02 实验设计）；
- 训练/实验日志分级（INFO/DEBUG），关键指标自动汇总。

## 5. 语言与表达

- 接口用代码签名表达（函数/类签名），不写模糊的「处理数据」；
- 目录结构必须与实际可建目录一致，不允许「示例结构」敷衍；
- 技术选型理由要具体：写「选 X 因为生态成熟、文档全、支持异步」，不写「X 是最佳选择」（绝对词警戒见 `通用写作规范.md` §2.5）；
- 架构术语冻结：依赖规则、边界、适配器、组合根、用例、DTO 等不换同义词；
- 测试命令、验收标准必须是可执行的命令与可观测的输出，不是「跑一遍测试」这种空话；
- 可视化与结果输出的约定要具体（格式、DPI、目录、命名），不写「图要好看」这类空话；
- 全文过一遍反 AI 腔自检（通用规范 §1）。

## 6. 引用与溯源

- 架构模式/技术栈选型若来自文献或参考 skill，标注来源（对应 `ref-external/README.md` 或文献）；
- 效果验证指标必须与 01 文档的评价指标一致；
- 禁止编造不存在的库、接口、性能数据；
- 版本号、依赖名必须真实（不存在或不确定的依赖标注「需确认」，不得虚构）。
